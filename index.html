Property Testing w TDD

Michał Dąbrowski

Witajcie wszyscy. Dzisiaj porozmawiamy o technice testowania, która fundamentalnie zmieniła to, jak myślę o pisaniu testów i pracy w TDD.

Siatka bezpieczeństwa testów jednostkowych

Oparte na przykładach

Testy jednostkowe weryfikują konkretne pary wejście/wyjście.

Sami wymyślamy przykłady

Testujemy to, co potrafimy sobie wyobrazić, a niekoniecznie to, co użytkownicy naprawdę zrobią.

Zarzucamy sieć

Każdy test jest węzłem w sieci i mamy nadzieję, że tą siecią złapiemy wszystkie błędy.

Testy jednostkowe są złotym standardem. Ale mają jedną dużą wadę: są oparte na przykładach. Zarzucamy sieć, a jej gęstość zależy wyłącznie od tego, ile przykładów mamy czas i cierpliwość napisać. A co, jeśli moglibyśmy przetestować WSZYSTKIE poprawne wejścia?

Problem z przykładami

Sami wymyślamy przykłady

Musimy samodzielnie wymyślić przykłady, a to nie zawsze jest proste.

Koszt utrzymania

Gęsta sieć oznacza dużo kodu do napisania, przeczytania i utrzymania.

Martwe pola

Ludzie (i LLM-y) mają uprzedzenia poznawcze i łatwo przeoczają edge case'y.

Często nie zależy nam na konkretnych przykładach

Chcemy wiedzieć, czy funkcja działa ogólnie.

Nawet gdy piszemy dobre przykłady, często nie zależy nam na konkretnych punktach danych. Tak naprawdę chcemy sprawdzić, czy dana funkcja ogólnie zachowuje się poprawnie. A jeśli spróbujemy stworzyć bardzo gęstą sieć, kończymy z ogromną ilością kodu do utrzymania. Właśnie tutaj wchodzi Property Testing.

Property Testing: zmiana paradygmatu

Oparte na przykładach

Dla A oczekuj B

Oparte na właściwościach

Dla WSZYSTKICH poprawnych wejść ta właściwość zachodzi.

Property Testing odwraca sposób myślenia. Zamiast mówić: "Dla A oczekuj B", mówimy: "Dla WSZYSTKICH poprawnych wejść ta właściwość powinna zachodzić." Przestajemy skupiać się na pojedynczych przykładach, a zaczynamy na niezmiennikach. Zobaczmy, jak to wygląda w praktyce.

Jak działa Property Testing

  1. Zdefiniuj Arbitrary
    Opisz kształt swoich danych wejściowych.
  2. Wygeneruj przykłady
    Biblioteka tworzy setki wejść, z naciskiem na edge case'y.
  3. Sprawdź właściwość
    Dla każdego wygenerowanego wejścia niezmiennik musi zachodzić.
Mechanika jest prosta. Najpierw definiujemy szablon wejścia, nazywany Arbitrary. Potem biblioteka generuje ogromną liczbę przykładów. Na końcu uruchamia każdy z nich przez nasz test. To generowanie nie jest przypadkowe; silnik aktywnie poluje na przypadki brzegowe. Uczyńmy to bardziej konkretnym na prawdziwym przykładzie.

Przykład: slugify()

🔗

slugify() — mały utility, który zamienia dowolny string w slug przyjazny dla URL-i

export function slugify(text: string): string {
  return text
    .toLowerCase()                   // Convert to lowercase
    .trim()                          // Remove leading/trailing whitespace
    .replace(/[^\w\s-]/g, '')        // Remove non-word chars
    .replace(/[\s_-]+/g, '-')        // Spaces/underscores to single dash
    .replace(/^-+|-+$/g, '');        // Remove leading/trailing dashes
}
Oto prosta funkcja slugify. Bierze string i zwraca slug przyjazny dla URL-a. Małe litery, bez znaków specjalnych, myślniki zamiast spacji. Dość proste, ale jak przetestować to porządnie? Spójrzcie na wymagania: one SĄ właściwościami.

Wymagania są właściwościami

Wymagania definiują niezmienniki wyjścia: warunki, które muszą zachodzić dla każdego poprawnego wejścia. To sprawia, że można je bezpośrednio przetłumaczyć na właściwości.

import fc from 'fast-check';

test('output should never contain whitespace', () => {
  fc.assert(
    fc.property(fc.string(), (originalString) => {
      const slug = slugify(originalString);
      return !/\s/.test(slug);
    })
  );
});
Sam test jest zwięzły. Ale podczas wykonania fast-check wygeneruje setki stringów wejściowych, w tym puste stringi, stringi z tabami i nowymi liniami, emoji, bardzo długie teksty, i sprawdzi, czy właściwość zachodzi dla każdego z nich. Ten jeden test zastępuje dziesiątki ręcznie zapisanych przykładów. Ale fast-check robi więcej niż tylko losowe generowanie stringów.

Losowe, ale nie bezmyślne

Puste stringi

Oraz stringi z bajtami null

Emoji i non-ASCII

Unicode'owe edge case'y

Bardzo długie stringi

Testowanie granic wytrzymałości

Wartości graniczne

Maks/min integerów, długość zero

Możecie się zastanawiać, czy to po prostu Math.random. Nie. Biblioteki do Property Testing używają generowania ukierunkowanego. Silnik wie, że błędy zwykle chowają się w ciemnych zakamarkach, więc celowo próbuje takich problematycznych wzorców. A kiedy test nie przejdzie, biblioteka robi jeszcze coś sprytnego.

Shrinking: znajdowanie minimalnego przypadku

Początkowe niepowodzenie

" ¥ \t \n © £ ÿ 🚀 ∆ … "

Chaotyczny string 100-znakowy. Co dokładnie spowodowało błąd?

Po shrinking

"\t"

Minimalny reprodukowalny przypadek: nasz kod nie obsługuje tabów

  • Test nie przechodzi - 100 znaków
  • 50 znaków
  • 10 znaków
  • 3 znaki
  • Minimum: "\t"
Kiedy test nie przechodzi, losowe wejście może być trudne do odczytania. Czy chodziło o tab? Nową linię? Długość? Biblioteka rozwiązuje to przez shrinking: ponownie uruchamia test z coraz prostszymi wejściami, aż znajdzie minimalny reprodukowalny przypadek. Teraz dokładnie wiemy, co się stało: nasz kod nie obsługuje poprawnie tabów. Ten minimalny przypadek staje się punktem startowym dla naszego cyklu TDD.

Generator "następnego czerwonego testu"

  • Test właściwości znajduje kontrprzykład: "\t"
    Red
  • Wyodrębnij go do utrwalonego testu jednostkowego
    Red
  • Popraw kod, żeby test przechodził
    Green
  • Refaktor i dalsza praca
    Refactor
W workflow TDD używamy tych odkryć, żeby napędzać postęp. Kiedy Property Testing znajduje kontrprzykład, nie poprawiaj od razu kodu. Najpierw wyodrębnij ten konkretny przypadek do osobnego testu jednostkowego. Testy właściwości uruchamiają się za każdym razem z innymi seedami, więc utrwalamy regresję. To tworzy pomost między testowaniem generatywnym a naszym stałym zestawem testów regresyjnych. A teraz zobaczmy, jak Property Testing radzi sobie z czymś bardziej złożonym.

Przykład: edytor z Undo

🔄

Edytor tekstu, który przyjmuje różne komendy i wspiera operacje undo oraz redo.

type Command =
  | { type: 'insert', position: number, text: string }
  | { type: 'delete', start: number, end: number }
  | { type: 'replace', start: number, end: number, text: string }
  | { type: 'truncate', length: number };

const commandArb = fc.oneof(
  fc.record({ type: fc.constant('insert'),
              position: fc.nat(), text: fc.string() }),
  fc.record({ type: fc.constant('delete'),
              start: fc.nat(), end: fc.nat() }),
  fc.record({ type: fc.constant('replace'),
              start: fc.nat(), end: fc.nat(), text: fc.string() }),
  fc.record({ type: fc.constant('truncate'),
              length: fc.nat() })
);
Wyobraźcie sobie, że testujemy edytor tekstu z komendami Insert, Delete, Replace i Truncate, z których każda wspiera Undo. Ręczne kodowanie każdej permutacji operacji to koszmar. Zamiast tego generujemy losowe sekwencje komend. A teraz sama właściwość.

Tysiące przypadków brzegowych w jednym teście

test('undoing all actions restores initial state', () => {
  fc.assert(
    fc.property(
      fc.array(commandArb, { minLength: 1, maxLength: 20 }),
      (commands) => {
        const editor = new Editor();
        const initialState = editor.getContent();

        commands.forEach(cmd => editor.execute(cmd));
        commands.forEach(() => editor.undo());

        expect(editor.getContent()).toBe(initialState);
      }
    )
  );
});
Właśnie przetestowaliśmy tysiące ścieżek użytkownika w około 20 linijkach kodu. Komentarz pokazuje eksplozję kombinatoryczną: już dla 3 operacji mamy niemal 370 000 permutacji. Przy 100 operacjach to 1.6 razy 10 do potęgi 60. Żadna liczba ręcznie pisanych testów nie jest w stanie z tym konkurować. Property Testing może też pomóc przy migracji systemów legacy.

Najważniejsza ukryta właściwość

Fuzzing

"Kod nie powinien się wysypywać" to też właściwość. W testach jednostkowych wejścia są bezpieczne; w testach właściwości wejścia są dzikie

Nieznane bazy kodu

Szczególnie wartościowe, gdy kod nie jest dobrze znany: systemy legacy i kod generowany przez AI

Jest jedna właściwość, której często nawet nie zapisujemy: kod nie powinien się wysypywać. W testach jednostkowych to nudne, bo nasze wejścia są bezpieczne. W Property Testing wejścia są dzikie. Samo sprawdzenie, że nasza funkcja nie rzuca wyjątku przy chaotycznych danych, nazywa się fuzzing. To niesamowicie wartościowe dla kodu legacy albo kodu generowanego przez LLM-y, gdzie możemy nie znać oczekiwanego wyniku, ale na pewno wiemy, że NullPointerException oznacza porażkę. Złóżmy to wszystko w całość.
